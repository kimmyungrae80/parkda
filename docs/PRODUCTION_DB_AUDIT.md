점검 상태: 미점검. 이 개발 계정으로는 운영 DB에 접근할 수 없다. DB에서 직접 확인된 항목은 없다.

## 1. 접근 권한 확인 결과
- 이 계정의 Supabase 조직(`myungraekim's Org`)에 운영 프로젝트가 없다. 프로젝트 목록에는 `pyeongnam-origin`, `eventon-web`, `cheerpop-app`, `oneulbari` 만 있다.
- 다른 경로로 우회하지 않았다. 공개 저장소의 anon 키로 스키마를 조회하는 방법도 쓰지 않았다.
- 실행한 것은 기존 감사 스크립트 `supabase/audit/parkda_store_readonly_audit.sql` 이 읽기 전용인지 검사한 것뿐이다 (쓰기 구문 없음). 운영 DB에는 아무것도 실행하지 않았다.

## 3. 저장소 코드로 확인된 사실
- 브라우저가 anon 키로 `parkda_store` 를 읽고 쓴다 (`dbLoad`, `dbSave`). 쓰기는 upsert 방식이다.
- 저장 키: `match_<코드>` (경기 전체, 점수 포함), `my_<전화번호>` (참가 경기 코드 목록), `clubs`, `early_adopters` (전화번호 포함).
- RLS가 열려 있다면 anon 키를 가진 누구나 경기와 점수를 읽고 바꿀 수 있다. 이 키는 공개 저장소와 웹페이지에 있다.
- 회원정보: 로그인 시 이름, 전화번호, 소속이 기기 localStorage(`pd_user`)에 저장되고, 저장 함수를 통해 서버에도 저장될 수 있다.
- 관리자: 관리자 비밀번호가 클라이언트 코드에 있다. 공개 저장소 이력에도 남아 있다. 관리자 판단은 `admin_ok` 값으로도 이뤄지므로 브라우저에서 임의로 권한을 얻을 수 있다. 값 자체는 이 문서에 기록하지 않는다.

## 4. 즉시 필요한 조치 (승인 필요, 실행하지 않음)
1. 운영 DB의 RLS 상태를 확인한다. 꺼져 있거나 anon 쓰기가 열려 있으면 쓰기 정책을 막는 변경을 최우선으로 검토한다.
2. 관리자 비밀번호를 바꾸고 클라이언트 코드에서 제거한다. 서버 인증 전까지 관리자 기능은 중지를 권고한다.
3. 전화번호가 들어 있는 `early_adopters` 와 `my_<전화번호>` 키의 보존·삭제 정책을 정한다.

## 5. P3~P6 신규 구조와의 충돌 가능성 (추정, 확인 필요)
- 신규 설계 테이블명(profiles, clubs, club_members, meetups, games, club_dues 등)이 운영 DB에 이미 있을 수 있다. 운영 감사 결과로 확인하기 전까지 같은 이름으로 `create table` 하지 않는다.
- 공개 데이터 테이블 `park_courses`, `park_tournaments` 도 이름 충돌을 확인해야 한다.
- 기존 키-값 구조와 신규 정규화 테이블은 병행 운영한다. 데이터 이전 방법은 별도 승인 후 정한다.

감사 결과를 공유할 때 행 데이터는 보내지 않는다. 다음만 보낸다.
