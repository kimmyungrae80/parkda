# 개인정보 노출 대응 기록 (PARKDA)

이 문서에는 실명, 전화번호, 점수 값을 적지 않는다. 식별은 커밋 해시와 개수로만 한다.

## 1. 무엇이 노출됐나

| 항목 | 내용 |
|---|---|
| 위치 | `index.html` 앱 초기화 코드 (기기에 샘플 경기 자동 주입) |
| 내용 | 실제 참가자 이름 **21명(작성자 포함)**, 1경기의 참가자별 홀 점수 기록 |
| 전화번호 | 실제 값 없음 (입력란 placeholder만 확인) |
| 도입 커밋 | \`8d0c70c\`, \`99fe4d1\`, \`a9fe760\` (2026-04-19 ~ 04-20) |
| 현재 상태 | 작업 트리에서는 제거됨. **이력과 공개 브랜치에는 남아 있음** |

## 2. 노출 범위 (확인 결과)

| 위치 | 이름 포함 개수 (git grep) | 공개 여부 |
|---|---|---|
| \`origin/main\` (마지막 커밋 \`60ead74\`) | 20 | **공개 저장소** |
| \`origin/feature/parkda-2\` (\`fb29634\`) | 20 | **공개 저장소** |
| 작업 트리 (이번 작업 후) | 0 | — |

- 저장소는 **PUBLIC**이다. 누구나 clone하거나 과거 커밋을 볼 수 있다.
- \`main\`에 포함돼 있어, 운영 사이트가 \`main\`에서 배포됐다면 **운영 페이지에도 노출됐을 가능성**이 있다. 배포 경로는 소유자가 확인해야 한다.
- 전화번호 패턴은 이력 전체에서 실제 값이 발견되지 않았다 (placeholder 2건만).

## 3. 이번 작업에서 한 것 (기존 데이터는 건드리지 않음)

- \`index.html\`에서 하드코딩 데이터와 주입 코드 7줄 제거. 주석으로 제거 사실만 남김.
- 주입은 \`localStorage\`가 비었을 때만 실행되던 코드였다. **제거는 기존 데이터를 지우거나 덮어쓰지 않는다.**
- 신규 기기는 샘플 없이 시작한다. 가상 테스트 데이터는 \`tests/fixtures/fictional_match.json\`에만 있다.
- 기존 사용자의 \`localStorage\` 및 Supabase 데이터는 변경하지 않았다. 회귀 테스트에서 기존 가상 경기가 로그인·생성·점수 입력 후에도 보존되는 것을 확인했다.
- 이력은 **재작성하지 않았다**. 커밋 삭제, force push, \`git filter-repo\`는 실행하지 않았다.

## 4. 소유자가 직접 해야 할 조치 (승인 필요, 실행하지 않음)

우선순위 순서.

1. **저장소를 비공개로 전환** (GitHub: Settings → General → Danger Zone → Change visibility → Private). 공개 상태가 계속되는 한 노출이 이어진다.
2. **운영 배포 확인**: 운영 사이트가 \`main\`에서 배포되는지 확인. 맞다면 제거된 버전으로 재배포하는 것이 필요하며, 배포는 별도 승인이 필요하다.
3. **이력 정리 여부 결정**: 이력에서 제거하려면 \`git filter-repo --replace-text\` 등으로 이름 문자열을 치환하고 모든 브랜치를 force push해야 한다. 되돌릴 수 없고, 기존 clone과 fork에는 그대로 남는다. 실행 전 백업과 팀 공지가 필요하다.
4. **GitHub 캐시 정리**: 삭제·재작성 후에도 GitHub 쪽 캐시 페이지가 남을 수 있다. 필요하면 GitHub Support에 민감 정보 삭제를 요청한다.
5. **키 재발급** (이력에 키가 있으므로 저장소 공개 여부와 무관하게 필요): YouTube API 키, 카카오 REST 키, 관리자 비밀번호.
6. **Supabase 점검 (읽기 전용)**: \`supabase/audit/parkda_store_readonly_audit.sql\` 실행. 같은 이름과 기록이 운영 DB에 있는지 확인만 하고, 삭제·수정하지 않는다.
7. **개인정보 유출 통지 검토**: 정보주체(참가자 21명)에 대한 통지 필요성과 시기를 개인정보보호 책임자와 검토한다. 법적 판단은 전문가 확인이 필요하다.
8. **관리자 기능 접근 통제**: 현재 관리자 비밀번호는 클라이언트 코드에서 확인된다. 서버 측 인증이 도입되기 전까지 관리자 비밀번호 변경이 필요하다.

## 5. 남은 보안 위험

- 공개 저장소 + 이력에 남은 개인정보 (위 1~4번 조치 전까지 지속)
- 브라우저 기반 권한(\`admin_ok\`, 표시 이름 일치, 역할 선택)은 우회 가능 (P0 보고서 2·5번)
- Supabase RLS 상태 미확인 (프로젝트가 이 계정에서 접근 불가)
- 서비스워커의 교차 출처 캐싱 (P1 작업에서 처리 예정)
