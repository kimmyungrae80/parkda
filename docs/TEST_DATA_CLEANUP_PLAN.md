# 테스트 회원·경기 데이터 정리 계획 (운영 DB)

상태: **계획 단계. 아무것도 실행하지 않았다.**
대상: 운영 Supabase 프로젝트 `szoxnkarkdxirbyxmzgr`. 이 개발 계정으로는 접근할 수 없다 (docs/PRODUCTION_DB_AUDIT.md).
삭제 SQL 초안: `supabase/cleanup/DRAFT_test_data_cleanup.sql` (주석 처리되어 있으며 실행 금지).

## 1. 현재 확인된 사실 (코드 기준 추정, DB 내용은 미확인)
- 데이터는 `parkda_store` 키-값 테이블 하나에 있다. 키 접두사: `match_<코드>`(경기), `my_<전화번호>`(참가 목록), `clubs`, `early_adopters`.
- 테스트 데이터와 실제 사용자 데이터를 구분하는 컬럼이나 표식이 코드에 없다. 따라서 **패턴으로 지우면 안 된다.**

## 2. 분류 기준 (소유자가 확정할 것)
| 분류 | 판정 기준 (안) | 처리 |
|---|---|---|
| 실제 사용자 경기 | 실제 참가자 이름·전화번호가 있고 점수가 있는 경기 | 보존 |
| 테스트 경기 | 메모·이름에 테스트 표식, 또는 소유자가 목록으로 지정 | 삭제 후보 |
| 전화번호 키 | `my_<전화번호>` 가 테스트 번호인지 소유자 확인 | 보존 또는 삭제 후보 |
| 동호회 | `clubs` 안의 테스트 클럽 | 소유자 확인 후 항목 단위 |
| 개인정보 | `early_adopters` (전화번호 포함) | 보존 정책을 먼저 정한 뒤 처리 |

## 3. 절차
1. **분류 (읽기 전용)**: 소유자가 SQL Editor에서 초안 1단계를 실행하고 키 접두사별 건수만 공유한다. 행 데이터는 보내지 않는다.
2. **백업**: 전체 내보내기 (JSON 또는 CSV)를 소유자 로컬 또는 비공개 저장소에 저장한다. 파일 해시를 기록한다. 공개 저장소에 올리지 않는다.
3. **복구 가능성 확인**: 백업 파일을 스테이징 프로젝트(별도 생성 후)에 넣어 복원이 되는지 확인한다. 복원 건수와 원본 건수가 같아야 한다.
4. **삭제 목록 확정**: 키 목록을 파일로 만들고 건수를 기록한다. 패턴 삭제(`like`)는 쓰지 않는다.
5. **최종 서면 승인**: 소유자가 대상 건수와 백업 위치를 확인하고 승인한다.
6. **삭제 실행**: 트랜잭션 안에서 실행하고, 삭제 건수가 목록 길이와 같을 때만 commit 한다.
7. **사후 확인**: 남은 건수, 실제 사용자 데이터가 그대로인지 확인한다. 결과를 이 문서에 기록한다.

## 4. 복구 계획
- 백업 파일 또는 백업 테이블에서 `insert ... on conflict do update` 로 해당 키만 되돌린다 (초안 4단계).
- 백업 없이는 삭제하지 않는다. 백업 검증이 실패하면 중단한다.

## 5. 현재 상태
- [ ] 1단계 분류 결과 수신 (소유자)
- [ ] 분류 기준 확정 (소유자)
- [ ] 백업 생성·해시 기록 (소유자)
- [ ] 스테이징 복구 리허설 (스테이징 프로젝트 생성 후)
- [ ] 삭제 목록 확정·서면 승인
- [ ] 삭제 실행 — 아직 실행하지 않음
